# Grading criteria

How this project is graded. Each criterion is scored Low (30%), Mid (70%) or High (100%) and weighted as shown.

| Criteria | Low (30%) | Mid (70%) | High (100%) |
| --- | --- | --- | --- |
| **1. It works (20%)** | The deployed app is unavailable, or crashes in the main workflows. | The deployed app runs, but some workflows fail or require workarounds. | The deployed app runs all workflows without errors, including invalid input. |
| **2. User interface and experience (20%)** | The interface does not fit the problem; screens are confusing, and users cannot complete tasks without help. | The interface fits the problem, but some workflows take unnecessary steps or give unclear feedback. | The interface fits the problem; workflows are direct, and results and errors are clearly shown to the user. |
| **3. Scope and ambition (20%)** | Little more than a solo project in size and features. | Several features that integrate into one product. | Substantial features that go well beyond a solo project, implemented consistently. |
| **4. Verification (10%)** | No tests, or tests that do not check the required behaviour. | Tests cover the main workflows, but miss rejected actions or edge cases. | Tests cover accepted and rejected actions and edge cases, and all pass on `main`. |
| **5. Security (10%)** | Credentials are in the repository, or sensitive data is exposed or stored insecurely. | No credentials in the repository, but gaps in access control, input validation, or dependencies. | Access control and input validation are enforced; dependencies are minimal, pinned, and without known vulnerabilities. |
| **6. Repository walkthrough (20%)** | Members cannot explain how the project is built or where its parts are. | Members explain what the main parts do, but not why they were built that way or their limits. | Members explain how the project is built, why, what its limits are, and how it could change. |
